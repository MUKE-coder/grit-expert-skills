# grit-security

Grit ships the defences. Your job is to use them correctly, to know what they
do and do not cover, and to read a scan without either ignoring it or
panicking at it.

```bash
grit docs search "security"
grit docs search "authorization"
grit routes                    # the route table, with what guards each route
grit doctor                    # misconfiguration, including security ones
```

## What is already there

Auth with JWT plus refresh, server-side sessions with rotation and replay
detection, idle and absolute timeouts, per-device revoke. RBAC. Per-resource
policies. 2FA and passkeys. OAuth. API keys in two kinds. An audit trail.
Sentinel as a WAF. Scout as a scanner.

**Do not hand-build any of it.** A hand-rolled session store or permission
check is the highest-risk code in a project and it will not have had the
attention these have.

## Authorization is where the bugs are

Authentication is mostly solved by the framework. Authorization is per
product, and it is where the real holes are.

**Ownership is enforced in SQL, not in Go.** An `--owned-by` resource filters
by the owner column in the query. Filtering after fetching is a leak waiting
for the one code path that forgets, and it is also slow.

**The frontend hiding a button is not authorization.** Every admin screen must
have an API-level gate behind it. The honest test is to call the endpoint
directly with a low-privilege token and see what comes back.

**Policies are per resource and they are files.** `internal/policies/` holds
them and `policies.go` registers them. If a resource has no policy, find out
whether that is deliberate.

**A role check at the layout level, not per page.** A new page in a protected
group should inherit the gate rather than needing somebody to remember it.

The route table is the ground truth for what is protected:

```bash
grit routes
```

It is generated by parsing the route files into `internal/access`, because
gin exposes a route's last handler and nothing in front of it, so the
middleware chain cannot be recovered at runtime. That is also why the admin's
routes screen has no access column: an invented one would be a guess presented
as fact. A public route gets an empty chain, never an inferred one.

## The sign-in path has four layers

Worth knowing before you change anything near it, because they interact:

1. Rate limiting per address
2. Lockout on the (address, account) pair, not on the address alone, so one
   person's mistakes behind an office NAT do not lock out everybody sharing
   that egress
3. A progressive delay
4. The credential check itself

Two rules. **A locked account must answer exactly like a wrong password**, or
the difference is an account-existence oracle. And the progressive delay has a
timing trap: if the delay only applies on failure, the response time tells an
attacker whether the password was right before the lockout does.

## API keys

Two kinds, and the distinction is the security model:

- **Publishable**: safe in a browser or a mobile app. Reaches endpoints marked
  `--public` and nothing else.
- **Secret**: server to server, and its plaintext exists only at the moment it
  is minted.

Which is why the seeder prints a secret key **only in development**. A log
line outlives the terminal: it ships to an aggregator, is kept for ninety
days, and is readable by everyone who can read logs. If you add anything that
mints a credential, that is the standard it is held to.

`--public` is read-only. A public endpoint that writes is hand-written and
must **not** go on the URL-cached public group, or the first caller's response
is served to everybody.

## Sentinel, the WAF

It sits in the request path and blocks things as they happen. It is not the
scanner and the two are not substitutes: one defends, the other looks.

```bash
grit docs search "sentinel"
```

The floor version matters and `grit doctor` reports a project left behind.
When a WAF version is raised for a security reason, a project that stayed put
is still exposed, which is the whole point of the floor.

One thing to know: a rich-text field needs a body-inspection exclusion,
because a WAF looking at HTML in a POST body sees an attack. The generator
adds it; if you hand-write an endpoint that accepts HTML, you add it.

## Scout, the scanner

Two different scans and neither does the other's job:

```bash
# the live app: headers, cookies, TLS, DNS, exposed files, the route table
scout scan --target http://localhost:8080

# the source: secrets, dangerous sinks, unpinned and vulnerable dependencies
scout scan --repo .

# a CI gate, counting only what is new
scout ci --repo . --fail-on high --new-only
```

The mounted dashboard at `/scout/ui/` runs the live checks and keeps history
so you can diff. It does not run the `code.*` checks.

### Reading a scan without wasting a day

A clean Grit project scores about 73 findings and **none of them is a way
in**. Know what they are before you start chasing:

- About 62 are caret ranges in `package.json`. A real decision about supply
  chain, not a hole.
- Signing keys in test files. A test that signs a token has to contain a key.
- The demo users' shared password in the seeder, which refuses to run outside
  development.
- `golang.org/x/crypto` and `disintegration/imaging`. Both are **module graph,
  not build**: nothing imports `openpgp` and the TIFF decoder is never
  registered. Neither has a fixed version to move to.

That last distinction is the one to internalise. A scanner that reads your
dependency list answers "is this version present". `govulncheck` answers "is
this code reached", which is the question that decides whether to act:

```bash
govulncheck ./...
```

A finding that `govulncheck` does not confirm is usually a version in the
graph that no code path touches. Record the decision rather than re-deciding
it every scan: Scout can mark a finding accepted with an expiry date, which
reopens itself, and that is the difference between deciding to live with
something and forgetting about it.

**Bugs in Sentinel, Scout, Pulse or GORM Studio go to their own repos.** They
are separate libraries. Never patch them inside Grit and never work around one
silently: file it, then put the issue number in the comment next to the
workaround.

## Before you say it is secure

- `grit routes` and read it. Every sensitive route has a guard
- Call a protected endpoint with a low-privilege token, and with none
- `govulncheck ./...`
- `grit doctor`, and fix what it says about versions and weak settings
- `scout scan --repo .` and triage honestly against the list above
- Confirm no credential is printed outside development

And say what you did **not** check. A security report that reads as complete
when it covered the API and not the mobile client is worse than one that names
its own scope.
